Usage guidance

Conventions for choosing between overlapping components, for signalling failures and blocked workflows, and for deciding when compact density is appropriate. The components are documented individually; this page is about picking the right one.

Choosing a container

Four components overlap as "a box with a heading". Choose by what the content is:

  • Summary block - structured facts about one thing: metadata, key-value rows, per-row actions. The workhorse for detail pages. If the body is a definition list, it's a summary block.
  • Queue card - an entry point to somewhere else: a workflow stage with counts and a single "open" CTA. If the point of the box is to leave it, it's a queue card.
  • Article card - one article in a scanning list (an inbox row). Never use it as a page section; it exists to be repeated.
  • Panel - the outcome of a just-completed action, at the top of a completion page ("Decision sent"). One per page, and only after an action.

Failures, unsaved work, and blocked workflows

  • A failed action gets a notice in the error kind at the top of the content area, naming what failed and what to do next. Field-level problems additionally use the form error pattern (message above the control, form-group-error).
  • Unsaved work: warn before it can be lost, not after. Use warning-text beside the control that would discard it; don't rely on a browser dialog.
  • A blocked workflow states the blockage and reorders the controls: the actions that resolve the blockage are enabled and listed first; the action being blocked renders as an inert placeholder (btn is-disabled with aria-disabled="true"), not as an enabled primary button. The peer-review reference page shows the pattern in its Status rail.
  • Emphasis is a budget. Status tags, alert pills, coloured rails, and primary buttons compete; a page should have at most one primary button and reserve colour for exceptions and the next meaningful action. If everything is highlighted, nothing is.

Density

Voyager's compact scale (11-15px) is tuned for scanning chrome: queues, metadata, status labels, tables - dense pages an editor reads dozens of times a day. It is not for reading. Use the larger sizes (--fs-md and up, comfortable line lengths) for:

  • instructions and hint text the user must actually read before acting;
  • decision content - anything the user is asked to weigh up (review text, revision requests);
  • confirmation and completion pages.

Uppercase 11px labels are for repeated, learned labels (status tags, section labels), never for one-off instructions.

Narrow screens keep task priority

Below 1100px, layout-with-rail collapses to one column and the rail follows the main content. If the rail carries the page's essential status and actions (as on the peer-review screen), add rail-first-narrow to the rail so it moves above the main content instead. Leave it off for rails holding secondary reference material.
