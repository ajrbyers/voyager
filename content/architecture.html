Architecture

Voyager uses CSS custom properties and native nesting, with no preprocessor or framework. Its file structure and token conventions are adapted from Memory Alpha.

Layer order

Styles load in this order: settings, reset, elements, components, and utilities. This is an import order, rather than a set of CSS @layer rules. Override utilities use !important to take precedence over component styles. 

settings  →  reset  →  elements  →  components  →  utilities
LayerFileContains
Settings settings.css Tokens - colour, type stacks, type scale, space scale, layout. Two-tier: raw tokens (--colour-grey-7) plus semantic aliases (--colour-fg).
Reset reset.css Box-sizing, margin / padding zeroing, list-style stripping where appropriate.
Elements elements.css Typography and link styles set on element selectors only (body, h1, a, p, …). No classes.
Components components/<name>/<name>.css One namespaced root class per component, all declarations nested under it with native &. No BEM.
Utilities utilities.css Single-purpose helper classes (.muted, .mono, .visually-hidden, .stack, .cluster). Win over component styles.

Component files

Each component has a stylesheet and a Jinja macro. Components with interactive behaviour also have a JavaScript module. Documentation pages contain usage guidance and examples rendered from the macros. Django keeps static files and templates in separate trees, so a component's source is split by type:

  • voyager/static/voyager/components/<name>/<name>.css - root class matching the name, native nesting, no unscoped element selectors
  • voyager/jinja2/voyager/components/<name>/<name>.j2 - Jinja2 macro for production use

The canonical markup and usage guidance for each component live on its documentation page at content/components/<name>.html, alongside the copy-pasteable HTML and Jinja2 examples. Those pages are docs-site content, not part of the shipped design system.

The CSS opens with the root class and nests everything inside it with the native & selector. Variants are extra flat classes composed in the markup - not BEM modifiers. 

/* button.css - root class is .btn, everything nests under it.
   Variants compose as additional flat classes in the markup. */

.btn{
  font-family:var(--font-sans);
  background:var(--colour-surface-grey);
  …
}
.btn:hover{ … }

/* Variants - extra classes, not BEM modifiers */
.btn-primary{ background:var(--colour-success);color:var(--colour-white) }
.btn-warning{ background:var(--colour-error);   color:var(--colour-white) }

/* Sizes compose with any variant */
.btn-small { padding:4px 8px 3px;font-size:var(--fs-sm) }
.btn-large { padding:9px 14px 8px;font-size:var(--fs-lg) }

Variant classes

Add variant classes alongside the component's base class. For example, btn btn-primary btn-large produces a large primary button. Any combination is one class list: 

<button class="btn btn-primary">Save</button>
<button class="btn btn-primary btn-small">Save</button>
<button class="btn btn-warning btn-large">Delete</button>

Tokens - two-tier system

All design tokens live on :root in settings.css. Two tiers:

  1. Raw tokens - the underlying value: --colour-grey-7: #1f2328
  2. Semantic aliases - point at raw tokens by role: --colour-fg: var(--colour-grey-7)

Raw tokens define values such as colours and spacing. Semantic tokens assign those values to roles, such as text, links, and backgrounds. Use semantic tokens in components so themes can change those roles consistently - dark mode remaps the semantic aliases in a single [data-theme="dark"] block. There are two documented exceptions: raw white on the fixed avatar colours, which do not change with the theme, and some earlier components that pair raw white with their own dark-mode overrides. New components use --colour-fg-on-emphasis for text on solid emphasis backgrounds. 

:root {
  /* Raw */
  --colour-grey-7:  #1f2328;
  --colour-blue-5:  #0969da;
  --colour-green:   #00703c;

  /* Semantic aliases - components reference these */
  --colour-fg:      var(--colour-grey-7);
  --colour-accent:  var(--colour-blue-5);
  --colour-success: var(--colour-green);
}

Loading styles

Link to index.css to load Voyager's styles. It imports the component stylesheets and shared settings in layer order. Each imported stylesheet remains a separate file. 

<link rel="stylesheet" href="/voyager/assets/css/index.css">

In a Django project, collectstatic gathers index.css and its layers, and a manifest storage backend hashes and rewrites the @import chain for production cache-busting - no separate bundler step.

Sources
