Tag picker

An HTMX-driven autocomplete for many-to-many relationships. Selected items render as removable chips; a search input queries the server, which returns matching items and an optional "Create" action for values that don't exist yet.

Open with results

The search endpoint returns the results partial: matching items first, then a highlighted "Create" action when the query doesn't exactly match an existing item. When nothing matches and creation isn't allowed, a no-matches message is shown.

Server contract

The widget expects three endpoints:

  • Search - GET with a q parameter. Returns the tag_picker_results() partial, which HTMX swaps into the .tag-picker-results container. Triggered on input changed delay:200ms and on focus.
  • Add - POST with either item_id (an existing item) or name (create a new item, then add it). Returns the full tag_picker() widget, swapped via outerHTML.
  • Remove - POST per item (each chip carries its own remove_url). Also returns the full widget.

Notes

  • The whole widget (#tag-picker-{name}) is the swap target for add and remove, so the chip row, empty state, and results all stay consistent after every operation.
  • Only offer the create action (can_create=True) when the query doesn't case-insensitively match an existing item, and validate creation server-side regardless.
  • Each remove button carries an aria-label naming the item ("Remove Astrophysics") so screen readers announce what is being removed.
  • Results are real <button> elements, reachable with Tab from the search input. This deliberately avoids a half-implemented ARIA combobox; if full arrow-key listbox navigation is needed, that's a JavaScript enhancement to layer on later.
  • There is no non-JavaScript fallback - the widget requires HTMX. Where progressive enhancement is a hard requirement, pair it with a standard <select multiple> inside <noscript>.
  • The search input reuses .form-input from the form component - place the widget inside a .form-group with a .form-label in real forms.
